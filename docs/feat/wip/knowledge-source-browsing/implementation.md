# Implement knowledge section browsing

## Terminal page

Add a context-aware store page read alongside `GetSectionInventory`. Accept a parsed `int64` source ID, an optional typed position and an effective page size. Perform the following reads in one transaction.

1. Select the label, kind and stored count from `sources` by ID. An absent source takes precedence over cursor membership. Propagate SQL, scan and cancellation errors distinctly from an absent row.
2. Choose between two fixed SQL templates for `chunks` and `chunks_trigram`. The first page uses `chunks`. For a supplied position, check that the rowid belongs to the requested source in its own table. Bind the source and row IDs as Go `int64` throughout. FTS `source_id UNINDEXED` can compare an integer differently from its decimal text.
3. Select at most `limit + 1` rowids for that source in ascending order, strictly after the position when supplied. Close that cursor and fetch title and body for only the first `limit` identities in the same transaction and order. Compute byte lengths on stored bytes, including embedded NUL. Complete the read transaction before display work or writes to the output stream. Use the last returned row and its table tag for continuation only when lookahead found another row. [Inventory](../../../../internal/store/inventory.go) · [Schema](../../../../internal/store/schema.go)

In `cmd/capy/search.go`, dispatch by explicit flag presence. Replace the unconditional minimum positional argument check with mode-specific validation, using Cobra's changed flags to distinguish a supplied filter from its default. Keep keyword argument joining and its 1–100 limit. For browse, parse the ID, tag, rowid and range before selecting the target or credentials. Reuse the project DB and captured key, signal context, checked writes and close/checkpoint error handling. A cached page needs no file Read policy preparation. Map store outcomes as specified in the [outcomes table](design.md#outcomes).

Reuse the existing CLI display sanitization in a helper callable by CLI and MCP. Redact complete values before normalizing invalid UTF-8 and replacing controls. For new page and receipt metadata and MCP hit headers, budget the finished single-line representation, including quotes, complete escape sequences and any ellipsis. The existing CLI keyword formatter clips the safe label/title first and then quotes them. Keep that ordering when adding its browse position. Preserve safe line breaks and tabs in body previews and clip at a rune boundary. Frame preview lines as content so a stored newline cannot create a navigation instruction. An SQL-clipped title or body can conceal the end of a secret from the redactor. Apply the appropriate field budget to every metadata echo. Use numeric source IDs in browse hints. A clipped or redacted label is display text only. [CLI rendering](../../../../cmd/capy/search.go#L132)

## Continue after a ranked hit

Select `c.rowid` in the knowledge corpus and scan it alongside `SearchResult.SourceID` in `internal/store/search.go`. Attach the actual Porter/trigram origin at the layer read in `internal/retrieval/retrieval.go`, where the SQL executor knows its table. Preserve that pair on the result whose body wins fusion, fuzzy merging, reranking and federation. `MatchLayer` can become `rrf(porter+trigram)` even though one physical row supplied the displayed body. Keep location independent of the presentation string and ranking keys. The vault and run corpora keep their existing row mappers and anchors.

Format the hit's source ID and its position, for example `42` and `t.905`, directly from that winning row. This needs no second query, lookup by title or speculative read to discover whether a successor exists. Use one representation for the actual table/rowid pair if the compact-replies work has landed. Preserve any knowledge metadata supplied by the excerpt work. Both integrations can ship independently. Where keyword replies use response-local references, include browse arguments in the first full hit's 3,072-byte allowance. A later reference leads back to it. ## MCP page

Declare optional string `sections_of` and `after_section` on `capy_search` and update the mode and limit descriptions. Select browse by the presence of `sections_of` and reject an orphan `after_section` across both modes. In browse mode allow only those two names and `limit` in the tool argument map. Reject even empty keyword selectors, the singular `query` alias, mixed flags and malformed types. Parse the raw page size before calling the throttle. The current keyword `searchLimitArg` clamps to two and cannot validate a browse request of nine. Preserve keyword admission and its accepted inputs. [Schema](../../../../internal/server/tools.go#L232) · [Keyword coercion](../../../../internal/server/coerce.go#L144)

Call `throttle.advance(requested)` once. A blocked request returns before opening either store. For other browse requests call only the knowledge page read with `budget.limit`, bypassing keyword preflight, vault initialization and refresh. Build the notice from that same budget snapshot, using entries per page and a retry after reset for blocked browsing. Return admitted errors via the same notice and response tracking path as successful pages. Name the invalid field in validation errors without interpolating unrestricted input. Emit the source ID and position as bounded CLI flag fragments or MCP arguments. Repeat an explicitly requested limit on the continuation, subject to fresh admission on its next use.

## Verification

The [task fixtures](tasks.md) exercise both public interfaces. For performance, use the pinned encrypted driver and a populated store with approximately 50,000 unrelated 300-byte sections distributed across sources within the normal source-size limit. Place an eight-section source near each end. On an already opened store, measure five warmed calls for each of four cases: first page of the late source, interior continuation, partial final page of the early source and a cursor at its last row. Choose a limit that exercises lookahead (e.g. three). Include representative continuations from both mirror tables. Record the query plans and median full-page times through rendering to an in-memory writer. Separately measure a returned oversized legacy field (e.g. 1 MiB) to expose full-field redaction cost.

Use **250 ms median per ordinary page** on that fixture as the implementation's interactive target. Record the machine and figures with the task. Timing belongs in the benchmark record, outside normal unit-test assertions. If the query misses the target, inspect the measured scan and rendering costs, adjust the read path and remeasure before accepting it. A persistent lookup index would require an explicit migration and support for existing shared-DB writers. The original review measured identity-only scans at about 50 ms in the slow cases. [Baseline probe](review-design-2026-11-23.md#4-a-fast-middle-page-can-conceal-an-expensive-first-or-final-page--tech_risk)

Run the affected store, retrieval, CLI and server tests with both synthetic keys and `-tags fts5`. Compare returned ranks and the repository search-quality benchmark with the pre-change baseline. Update CLI help and the public tool reference with index, fetch, ranked-hit, EOF and stale-ID examples.
