# Design review of session byte accounting

**Original assessment at `6677d7b` — CONCERNS_FOUND, with two high and four medium findings.** A developer should be able to ask how many bytes this MCP server processed and returned, then ask again without the first report changing the workload. The original proposal allowed a failed submission to look like a complete byte reduction, and its tests missed a race with the first knowledge index. The [resolution](#resolution) records the decisions in the revised design.

Reviewed the [design](design.md), [implementation plan](implementation.md) and [tasks](tasks.md) at capy `6677d7b`. The [proposal overview](../knowledge-session-and-diagnostics.md), the search reply and fetched-page designs, and existing capy contracts were checked for interactions.

## P1 — High

**1. Counting an input while omitting its error reply can report 100% reduction for failed work.** `INCONSISTENT` · Confidence 10/10, reproduced through the handlers. The design deliberately counts submitted input even on failure. The implementation preserves existing response-tracking points. With a 64-byte store limit, a 128-byte inline index submission returned a 107-byte error. The snapshot recorded 128 input bytes, zero index calls and zero returned bytes. The current report said “No capy tool calls yet.” Under the proposed arithmetic those counters yield 100% reduction if rendered. Fetching the same 128-byte body also counted one attempted miss in both modes. The single-URL error contributed zero returned bytes, while the one-URL batch counted its entire 441-byte reply. [Report contract](design.md#report-contract) · [Tracking rule](implementation.md#report-overhead) · [Index exits](../../../../internal/server/tool_index.go#L60) · [Single fetch](../../../../internal/server/tool_fetch.go#L155) · [Batch fetch](../../../../internal/server/tool_fetch.go#L532)

Count the actual error reply whenever the handler has already charged the submission or body, including file-index failures after submission. Validation errors before measured work can keep their existing policy. Render input and prior-report overhead independently of whether the workload call map has any entries. Add a failed single submission and a one-item failed batch to acceptance. Also check the input-only snapshot possible between an input event and its reply. [Current empty branch](../../../../internal/server/tool_stats.go#L38)

**2. The concurrency test misses a race in the report itself.** `TECH_RISK` · Confidence 10/10, reproduced under the Go race detector. On a fresh server, running `handleStats` alongside the first `handleIndex` reported a read at `tool_stats.go:98` racing with publication of `s.store` at `server.go:153`. The writer uses `sync.Once`, but the optional inventory reader accesses the pointer directly. The MCP transport has concurrent workers. A race test limited to `SessionStats.Snapshot` and `Reset` can pass while users still hit this race. [Verification plan](implementation.md#verification) · [Report reader](../../../../internal/server/tool_stats.go#L97) · [Store initialization](../../../../internal/server/server.go#L150) · [Transport workers](../../../../internal/server/server.go#L262)

Give the report a synchronized way to obtain an already initialized store. Publish the handle after configuration, let a cold report skip the inventory, and release synchronization before database I/O. Exercise the two real handlers on a fresh server under `-race`. This preserves lazy initialization and keeps inventory queries outside the counter mutex.

## P2 — Medium

**3. Correct counters can still display rows that do not add up.** `INCOMPLETE` · Confidence 10/10, verified with the current formatter. The plan requires the operator to reconcile per-tool bytes and totals. `formatBytes` rounds every value independently to tenths of a binary kilobyte or megabyte. Two 60-byte rows each display `0.1KB`, and their 120-byte total also displays `0.1KB`. A one-byte reply displays `0.0KB`, even though it activates the 99.9% display cap. Require exact integer bytes in the workload rows, input components, totals and report overhead. Human-readable units can accompany them. Check the rendered values with two small rows as well as the 10,000-byte example. [Reconciliation requirement](implementation.md#report-overhead) · [Formatter](../../../../internal/server/tool_stats.go#L228)

**4. Reset attribution needs a rule for all recorded events.** `AMBIGUOUS` · Confidence 9/10, based on the observed purge result and the order of counter updates. The design assigns a late run completion to the interval where its callback fires. A single fetch also records body, response and deferred cache outcome separately. A stats call can take its snapshot before a reset and record its overhead afterward. A real successful `purge_all` in the probe left zero input and one cleanup response of 90 bytes in the new interval. A test that expects an all-zero first public report would reject current behavior. [Design assumptions](design.md#assumptions) · [Fetch update order](../../../../internal/server/tool_fetch.go#L108) · [Purge](../../../../internal/server/tool_cleanup.go#L84) · [Existing purge test](../../../../internal/server/tool_utility_test.go#L719)

Specify that each accounting event belongs to the interval in which the counter update occurs. A single request may contribute to two intervals. Define report overhead as completed report measurements at snapshot time. Verify the public post-purge report and one controlled crossing of a reset, including a late completion. A mutex race check alone cannot establish which interval owns a byte.

**5. The old public savings claims and the prior decision need an explicit replacement.** `INCONSISTENT` · Confidence 9/10, the current report, architecture and ADR make the old promises explicitly. The report presents a multiplier, estimated tokens saved, bytes that “never entered context,” and a second savings sentence. A 10,000-byte input with 2,000 bytes returned yields an 8,000-byte reduction under the new contract. The existing token row uses all input treated as kept out. Keeping those rows beside the new estimate would give two answers. ADR-013 also specifies the old formula and `0.0%` for zero processed bytes, while this design specifies an unavailable estimate. [Proposed arithmetic](design.md#report-contract) · [Current report](../../../../internal/server/tool_stats.go#L41) · [Tool description](../../../../internal/server/tools.go#L367) · [ADR-013](../../../adr/013-configurable-fetch-ttl.md#amendment-cache-outcome-visibility-2026-10-12) · [Architecture](../../../architecture.md#fetch-and-index-capy_fetch_and_index)

Name the rows the byte estimate replaces and remove the unsupported claims. Add an amendment to ADR-013 and update the architecture and tool reference with the new denominator, zero-input behavior and retained display cap. Check positive input with returned bytes greater than input too. The current helper produces `-20.0%` for 100 in and 120 out. The proposal correctly requires `0.0%` in that case.

**6. The fetch receipt uses a different meaning of “fetched” from the proposed report.** `AMBIGUOUS` · Confidence 10/10, both byte sources are visible in the fetch handlers. Stats charges an admitted HTTP body before conversion. The batch receipt labels the sum of successfully indexed, *converted* content lengths “KB fetched.” Large HTML with a short readable article will produce different values. A conversion or indexing failure can give the receipt zero bytes and stats a full body's worth. The separate cache estimate is `chunk count × 1,600` per hit. It cannot reconstruct either the original body size or wire traffic, and a chunking change can alter the estimate for identical HTML. [Proposed inputs](design.md#report-contract) · [Single-fetch display size](../../../../internal/server/tool_fetch.go#L155) · [Cache estimate](../../../../internal/server/tool_fetch.go#L515) · [Batch receipt](../../../../internal/server/tool_fetch.go#L539) · [Readable-page proposal](../readable-fetched-pages/design.md)

Use consistent labels for admitted body bytes and converted content bytes wherever a caller can compare them. Document the cache heuristic beside the estimate. One HTML fixture whose article is much smaller than its body, followed by a TTL hit, establishes all three meanings without introducing wire instrumentation.

## What is ready

- The feature answers a useful, measurable question about process-local byte flow. Its global floor and denominator handle repeated reads, cache-only activity and queries against previously retained data. Inline knowledge can already have been in the prompt. A host token or billing estimate would require evidence this server cannot collect.
- The producers already expose the required measurements. Inline input uses its length before the store call. Files and directories expose raw bytes offered to the store, including unchanged content, separately from partial reads and oversize probes. Label these as explicit MCP submissions. CLI ingestion, vault import and a search-triggered stale-file refresh have separate paths. [File submission](../../../../internal/knowledge/index.go#L132) · [Directory accumulation](../../../../internal/knowledge/directory.go#L453) · [Stale refresh](../../../../internal/store/stale.go#L118)
- Observed and captured run bytes already arrive together at owner completion. Capy's existing yielded execute, file and batch tests cover late output and individual children. The legacy sandbox field already includes observed output. A later MCP read adds returned bytes only. A public-handler assertion should compare the returned-byte delta to the serialized result for a structured read and to payload length for a text reply. The existing owner test calls the execution service directly for reads. [Owner counters](../../../../internal/server/stats.go#L59) · [Existing yielded-run test](../../../../internal/server/run_diagnostics_test.go#L94) · [Operator contract](../../../reference/runs.md#storage-policy-and-diagnostics)
- The assumptions, exclusions, task sizes, dependencies and verification steps are present. The change fits the existing in-memory snapshot and text renderer. Historical dashboards, per-agent ledgers, schema changes and a transaction spanning all inventories would add cost without improving this report.

**Verification.** Focused FTS5 tests passed for existing savings display, single/batch cache lifecycle, purge/reset and yielded run completion. Temporary Go test overlays exercised the existing handlers with synthetic credentials and storage. The separate cold-server race probe failed with the read/write pair in finding 2. These results establish the baseline for the design review. Acceptance of the new report requires its implementation.

The review found no P0 or P3 issues.

## Resolution

All six findings were confirmed. I checked the handler paths, the captured baseline probes, the existing tests and ADR-013 against the proposed fixes. Additional FTS5 probes used synthetic data. A 12,046-byte HTML body yielded a batch receipt of `0.0KB fetched` and a subsequent one-chunk cache estimate of 1,600 B. With an unavailable test store, both a zero-byte and a four-byte file reached indexing and returned untracked errors. A nine-byte file over the eight-byte admission limit also returned an error but never reached indexing. A 5,722-byte HTML fixture exceeding the parser’s nesting limit reached the conversion-error path in both fetch modes, so the acceptance test can use the current converter. The single call recorded zero replies and the batch recorded one.

| Original finding | Decision ready for implementation |
| --- | --- |
| 1. Failed reply coverage | Track the actual post-submission index error, including an empty file. Count eligible single-fetch errors and one whole batch reply. Preserve early rejection rules and render input-only snapshots. [Index and fetch replies](implementation.md#index-and-fetch-replies) |
| 2. Race during first index | Guard construction and optional access with the same mutex, publish after configuration and release the lock before inventory reads. Exercise cold concurrent handlers with the race detector. [Concurrent inventory](implementation.md#concurrent-knowledge-inventory) |
| 3. Rounded rows | Use integer bytes in every accounting row, including overhead. Verify that 60 B plus 60 B visibly yields 120 B. [Report contract](design.md#report-contract) |
| 4. Reset attribution | Record the interval at the time each counter is updated. Check the cleanup reply, a late completion and the distinction between interval start and uptime. [Reset and live inventories](design.md#reset-and-live-inventories) |
| 5. Old savings claims | Replace the multiplier, tokens and both context claims. The dated ADR decision supersedes the savings formula when implemented. The task list identifies the user-facing references to update with the code. [ADR-013](../../../adr/013-configurable-fetch-ttl.md#workload-byte-reporting-decision-2026-11-23) |
| 6. Fetch size meanings | Use exact admitted HTTP body bytes and successful index-input bytes on receipts. Keep the per-chunk cache estimate separate and name its basis. [Fetch contract](design.md#index-and-fetch-replies) |

**Design disposition — ready for implementation.** The [acceptance cases](implementation.md#verification) and [pending tasks](tasks.md) cover these decisions. The baseline race and tracking gaps remain reproducible in the current Go code.
