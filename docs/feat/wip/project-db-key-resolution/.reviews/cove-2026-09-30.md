# Isolated verification of project database key resolution

Date: 2026-09-30. Baseline: `d9e09c1`. Method: four independent general-purpose agents, each with no conversation history or proposed answer. Agents inspected code without reading this feature directory, inspecting credentials, editing files, or running tests. User selected approach C and requested isolated verification during `kk:design`.

## Initial answer

Capy obtains knowledge keys from the process environment for ordinary store opens and maintenance connections. The generated wrapper loads the main worktree's `.env` only for first-argument `serve` with an empty inherited key. A shared resolver should provide one selected key retained through checkpoint and close.

Database ownership should follow `DBProjectDir`: relative paths redirect linked worktrees to the main checkout, while absolute and XDG paths retain their current behavior. Commands that replace invalid config with defaults need explicit failure handling when credentials become configurable.

MCP doctor should use the existing independent FTS5 probe and initialize its knowledge store separately. Both committed wrappers and their generator need synchronized updates that preserve hook exit behavior. Vault credentials and `encrypt`'s new-passphrase input must remain separate.

## Independent verification

### Q1 Where do database operations obtain their keys

Agent: `cove_key_lifecycle` (general-purpose). Status: completed.

`NewContentStore` stores no key. `openDB` and `openSingleConn` independently call `RequireEncryptionKey`; recovery and reopening can reread it. Existing pools retain their original DSN, while maintenance can use a later environment value. Maintenance consumers include vacuum, FTS rebuild, explicit checkpoint, and shutdown checkpoint. Close shuts the pool before opening the checkpoint connection.

`ValidateEncryptionReady` checks for a key and a plaintext header; it does not authenticate. The ordinary store open authenticates with a canary. `encrypt` prompts for the old key and obtains the new key from `CAPY_DB_KEY` or a confirmed prompt.

Sources: [store.go](../../../../../internal/store/store.go) (`NewContentStore`, `openDB`, `openSingleConn`, `Close`, `Checkpoint`); [encryption.go](../../../../../internal/store/encryption.go); [encrypt.go](../../../../../cmd/capy/encrypt.go); [sqliteutil.go](../../../../../internal/sqliteutil/sqliteutil.go) (`OpenWithCanary`).

### Q2 How are project configuration and database paths selected

Agent: `cove_project_config` (general-purpose). Status: completed.

Commands prefer nonempty `--project-dir`, then `DetectProjectRoot`. Detection prefers `CLAUDE_PROJECT_DIR`, then cwd-based Git and ancestor detection. Explicit and environment paths are used without root or symlink normalization.

Configuration merges global XDG, selected-project `.capy/config.toml`, then selected-project `.capy.toml`. Main-worktree config is not reloaded. A read/parse/validation error discards the merged config. Knowledge commands then fall back to defaults; some warn and others discard the error. A test explicitly expects successful checkpoint fallback after malformed config.

All nonempty relative store paths, including `../` paths, use `DBProjectDir`; absolute and XDG paths do not redirect. Worktree detection failure falls back to the supplied project directory. Submodules are excluded. XDG hashing does not canonicalize symlinks.

Sources: [paths.go](../../../../../internal/config/paths.go); [loader.go](../../../../../internal/config/loader.go); [main_test.go](../../../../../cmd/capy/main_test.go) (`TestCheckpointSubcommand_BadConfig`); [serve.go](../../../../../cmd/capy/serve.go); CLI `which`, `dbsize`, `cleanup`, `checkpoint`, `doctor`, and `encrypt` in the same directory.

### Q3 How do the two doctors check FTS5 and readability

Agent: `cove_doctor` (general-purpose). Status: completed.

CLI doctor probes FTS5 in memory independently of knowledge access. MCP doctor uses `getStore().Stats()` for its FTS5 result, then calls stats again for knowledge diagnostics. Removing the first block also removes its store-initialization side effect unless the knowledge block calls `getStore` explicitly.

Stats initializes the store, so doctor can create, migrate, or recover a database. CLI doctor avoids creation after a failed path stat but currently treats all stat errors as absence. Both surfaces preserve returned initialization errors in the knowledge result. A successful stats result is not a full integrity check: count/classification query errors are suppressed inside `Stats`.

Sources: [platform doctor](../../../../../internal/platform/doctor.go) (`CheckFTS5`); [CLI doctor](../../../../../cmd/capy/doctor.go); [MCP doctor](../../../../../internal/server/tool_doctor.go); [store cleanup](../../../../../internal/store/cleanup.go) (`Stats`); [store.go](../../../../../internal/store/store.go).

### Q4 Which wrappers and hooks participate in credential loading

Agent: `cove_wrappers_hooks` (general-purpose). Status: completed.

Both generated wrappers source the whole main-worktree `.env` under `set -a`, which can change the vault key and other variables. The guard considers argument one and cwd, ignoring project flags. Missing knowledge keys can stop execution before binary discovery; old wrappers therefore require regeneration when key resolution moves to Go.

Claude hook handlers do not access either store. The generated Git pre-commit hook does access knowledge indirectly through wrapped `checkpoint`; failures must abort the commit. The separate DB-repo guard is keyless. Codex MCP configuration forwards both key variables; Claude launches the corresponding wrapper without an explicit key environment block.

Sources: [setup.go](../../../../../internal/platform/setup.go) (`capyWrapperScript`, pre-commit block, MCP generators); [hook.go](../../../../../internal/hook/hook.go); [checkpoint.go](../../../../../cmd/capy/checkpoint.go); [DB-repo setup](../../../../../internal/platform/setup_dbrepo.go); [artifact drift tests](../../../../../internal/platform/setup_artifacts_drift_test.go).

## Reconciliation

No initial claim was contradicted. The investigation's reproduction remains the runtime evidence; static verification does not prove which credential the original daemon inherited. The candidate resolver has not been implemented or tested.

## Additional findings and follow-ups

These findings are pre-existing and are not silently included in the key-resolution fix:

- `ContentStore.Stats` suppresses some aggregate-query errors. Deferred to a separate diagnostic correctness change because issue 122 concerns key-selection/open failures, which already propagate. Next step: return count/classification query failures and add tests that force a query error after successful initialization.
- Server shutdown and several deferred CLI closes discard `ContentStore.Close` errors. Deferred to a separate shutdown-error handling change; this design fixes key consistency within close, not general shutdown reporting. Next step: preserve/log close errors without hiding an earlier command error, with tests for failed checkpoints.
- CLI doctor conflates path-stat failures with absence. Include a narrow correction in this feature's diagnostic path: only `os.IsNotExist` means uninitialized; other errors must be reported as database-access failures.

## Final verified answer

The shared Go resolver is compatible with the existing package boundaries if the selected key reaches both ordinary and dedicated maintenance connections, configuration errors cannot change the intended target, and wrapper regeneration is part of rollout. FTS5 capability must be checked independently. Key rotation, vault scope, and existing database ownership rules remain separate contracts. These conclusions are supported by four completed independent code inspections; candidate behavior still requires the regression suite specified by the design.
