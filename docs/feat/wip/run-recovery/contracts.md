# Run recovery contracts

> Status: implementation-ready contract after author fresh-read check
> Parent: [design.md](design.md)
> Plan: [implementation.md](implementation.md)

## Authority and invariants

1. Execution cleanup stays a validated `(scope, state)` pair. No new accepted cleanup state is introduced. `terminal == (CompletedAt != nil && CleanupAccepted(cleanup))` remains the execution invariant.
2. An operator disposition is a separate, authenticated administrative record. It may authorize operational closure and future admission without making original cleanup complete or setting an original exit code, completion timestamp or terminal-persistence bit.
3. One shared `OperationallyClosed` rule accepts valid execution-terminal evidence or a valid disposition bound to the exact run/store/generation. Use it only for the administrative consumers identified here; never replace execution-proof validation with it.
4. Pending unresolved execution never expires or becomes safe merely because a lock is free, a PID is absent, or time passed. Unsupported identities/proof combinations remain errors.
5. Diagnostics/planning do not initialize, reconcile, maintain, publish policy, index or claim execution owners. Apply/upgrade use dedicated administrative attachment and close paths, not `execution.Service` or normal `Store.Close`.
6. Recovery is all-or-nothing for the reviewed store inventory. It does not execute, signal, adopt or resume application work. Existing permanent lock inodes remain in place.
7. No recovery/upgrade operation evicts retained history to fund itself. Normal subsequent TTL/quota maintenance remains separate and explicitly described.

## Persistent model

Schema 10 adds the following logical records. Implement explicit constrained SQL with indexed subject/dependency lookup; no full schema implementation is prescribed here. All records live in the same encrypted run database.

| Record | Required meaning and bounds |
| --- | --- |
| Incident | UUID; stable subject kind `run`, `owner` or `store`; subject identity and known slot/generation/run/batch IDs; bounded reason enum; attribution `recorded`, `inferred` or `unattributed`; first detection time; detection stage; last durable phase; optional recovery receipt reference. No program, output or raw backend error. |
| Recovery receipt | UUID; unique reviewed-plan hash; applied time; method `operator`; declared basis `groups_stopped` or `host_restarted`; current OS UID as local provenance, not identity proof; required sanitized explanation at most 1,024 UTF-8 bytes; immutable aggregate counts; charged bytes and audit deadline. |
| Run disposition | Unique run ID bound to store, original generation/slot and optional batch; receipt and incident references; byte-exact original result snapshot (existing 8-KiB limit) and its SHA-256 digest, cleanup pair and terminal bit; admission TTL/policy revision; fixed administrative retention deadline; charged bytes. Evidence/identity fields are immutable. Separate retention bookkeeping records payload state `retained`, `evicting` or `evicted` and eviction time/cause; it survives deletion of the run row. |
| Incident resolution membership | Immutable receipt-to-incident association, including owner/store incidents with no run. Preserve the subject/reason snapshot needed after registry reuse. |
| Batch resolution | Receipt/provenance references and separate operational-close/retention times once every child is operationally closed. Preserve original batch completion/expiry fields. |
| Disposed-run index state | Separate `run_search_state` row keyed by retained run ID, with bounded index state, coverage cursor and safe typed error metadata. Provision the table in schema 10; seed the row from the current normalized index view during disposition. Existing per-stream `run_search_progress` retains coverage/window positions. This mutable search metadata expires with payload, not with the independently retained audit. |
| Metadata additions | Store recovery revision; `runs.last_phase` as a required enum with no SQL default; disposition references on retained child manifests where needed. Existing cleanup columns also keep no defaults. |

Deduplicate only unresolved incidents by subject identity within the store, including historical generation. An unchanged repeated observation reuses the existing incident and original detection time. A resolved incident is immutable: a later incident for the same owner/store subject receives a new UUID/episode and revision, never the previous receipt. A disposed run cannot be executed again; a later identity/proof inconsistency in that run must fail validation rather than be excused by its old disposition. Add bounded reason/stage information only when new evidence materially changes an unresolved incident; increment recovery revision then. Never infer the original detection timestamp from a migration time. Historical phase may be `unknown`.

`recovery_revision` is a monotonic membership/disposition epoch, initialized to zero. Increment it transactionally when incidents are inserted or materially revised, quarantine markers change, a receipt/disposition commits, a batch gains administrative closure, or an audit group is marked/pruned. One increment per transaction is sufficient; identical retries/read-only work do not increment it. Refuse mutation on revision exhaustion rather than wrapping. Ordinary capture/index progress does not increment this epoch: those values are sampled per inspection page, while offline plan validation hashes the complete current evidence independently.

Supported last durable phases are `unknown`, `admitted`, `queued`, `authorized`, `compile` and `run`. Set admitted/queued in admission, authorized in the existing pending-proof update, and compile/run in the existing start callback. Do not add an extra capture write for every event. Detection stage separately identifies startup, helper wait, finalization, reconciliation or legacy inspection; it must not pretend to be a durably recorded execution phase.

The final schema requires `last_phase` to be `NOT NULL`, constrained to that enum, and to have no default. Migration copies legacy rows with an explicit `unknown` value into the rebuilt runs table; it does not leave an `unknown` column default behind. New single/batch admission must initialize `admitted`/`queued` explicitly at the store's insertion boundary (`prepareRun`/`insertRun` and batch admission), which rejects a missing or `unknown` phase. This is internal admission metadata, not a new user-supplied execution argument. An omitted or NULL phase must also fail at the database boundary. A nullable enum CHECK alone would not reject NULL, so that is not the selected model. Use the existing table-rebuild pattern and account for its temporary copy/WAL space; preserve row identities, payload/result bytes, indexes and foreign-key validity.

New incidents use typed causes such as `pending_cleanup`, `finalization_unpersisted`, `supervisor_lost` and `startup_uncertain`. `generation_mismatch`, invalid proof/manifests and unresolved structural inconsistencies remain diagnostic reasons that refuse application. `legacy_unattributed` is permitted for a structurally valid historical marker whose exact causal run is unavailable.

Incident/receipt fields are versioned and bounded. Subject IDs cannot become filesystem targets. Sanitization occurs before storing the explanation; reject an explanation that is empty/invalid/oversized after normalization. Do not print that stored explanation in admission errors or doctor. Explicit recovery-detail inspection may display its sanitized form.

## Incident publication and fail-closed fallback

`Service.quarantine` receives the known admitted run/generation and a typed stage/cause. It retains the current in-memory quarantine latch even if the storage write fails. Persist incident attribution and store quarantine together where possible. Reconciliation persists its incident and owner/global marker together under the existing registry lock and transaction.

An attribution failure must not lose the underlying refusal. Cache a bounded context for this owner's subsequent errors; do not claim it is durable. On restart, authenticated pending records/legacy markers remain the fallback. Inspection explicitly distinguishes known durable attribution, inferred candidates and unavailable attribution.

A still-live run with pending cleanup and no quarantine evidence is not an incident merely because it is unfinished. Ordinary read-only inspection never acquires owner-generation leases to speculate about liveness. Offline planning, after excluding all cooperating owners/helpers, may include well-formed abandoned pending rows as inferred recovery subjects even when an earlier attribution write failed.

A valid legacy global marker with no identifiable pending row is represented by a store-scoped incident. Operator recovery can resolve that reviewed store concern after the same shutdown/cleanup responsibility; it must not invent a run ID. Registry-generation mismatches, missing nonterminal batch children, malformed results and inconsistent proof copies are outside this override and fail with actionable `recovery_inconsistent` diagnostics.

## Read-only inspection

Public surfaces:

- `capy runs inspect [--run-id ID | --receipt-id ID | --plan TOKEN] [--cursor CURSOR] [--limit N] [--json]`.
- `capy_runs(action="inspect", ...)` with `run_id`, `receipt_id` or `plan` as mutually exclusive selectors, plus cursor and limit; no apply, confirmation or cleanup-basis arguments.
- CLI/MCP doctor and `capy_stats` reuse the bounded summary snapshot through the existing shared `runChecks`/`platform.CheckRuns` path. Task 1 verifies unchanged `RunsCompleted`, `RunsIncomplete`, `RunObservedBytes` and `RunCapturedBytes` during inspection. Normal tool-call/returned-response accounting still occurs and is not mistaken for duplicate run completion.

`--receipt-id`/`receipt_id` accepts only a recovery receipt UUID, exposed as `recovery.receipt_id` in affected results. It does not search incident or disposition IDs. A syntactically valid UUID with no receipt returns `receipt_unavailable`; invalid UUID syntax returns `invalid_argument`. There is no `--recovery-id` alias. Incident identity remains explicit in inventory entries without overloading the receipt selector.

Use an existing shared lifecycle lease, read-only authentication and a read transaction. Never create missing paths/locks or invoke normal attachment/close maintenance. **Accepted exception (2026-10-29, operator decision during Task 1):** if a closed store has no WAL, acquire a fresh nonblocking exclusive lifecycle lease (never convert a shared lease), recheck WAL absence and refuse a nonempty rollback journal, then use an immutable read-only connection. Keep that lease until the database handle closes. This prevents SQLite from creating absent WAL/SHM sidecars; inability to obtain exclusivity returns an explicit retry instruction. Active WAL inspection remains shared and must prevent SQLite sidecar creation even if another connection closes during attachment. Inspection has the existing two-second budget; pages use 1–64 entries and the configured serialized response limit. Bind continuations to store identity and the inspected recovery revision; changed evidence returns a stale-view instruction instead of silently skipping new subjects.

The accepted exclusive fallback briefly excludes other store attachments: an ordinary nonblocking attachment can return lifecycle-busy during that snapshot. This was the contention tradeoff presented to and accepted by the operator on 2026-10-29; it does not admit or retry an execution. Retry attachment after the inspection completes. No automatic command replay or weakening of lifecycle exclusion is introduced.

Return selected owner/store identity, schema compatibility, effective admission status, durable/inferred/unattributed counts, bounded subjects and missing evidence, last-recorded state/phase, receipt/disposition status, availability of retained output and a fixed action code plus safe next-step text. Keep a safely quoted executable inspection command separate from explanatory prose; omit executable text when its selected path cannot be represented safely. Doctor shows blockers separately from its recent sample. A partial/unavailable detail query remains visibly incomplete; it never reports an empty blocker inventory as a healthy store.

Inspection reports **recorded** quarantine and incidents, not a prediction that `GuardAdmission` will pass. Pending rows without recorded attribution are separate `unattributed_pending` observations: without acquiring owner leases, inspection cannot distinguish a healthy live run from abandoned execution awaiting reconciliation. Such rows neither become confirmed incidents nor prove healthy admission. State this limit in the result instead of reporting their processes as live or their store as definitely unblocked.

Each page is one read transaction with its own observation time. Schema-10 continuations bind selection/filter, ordered position, store identity and recovery epoch; an epoch change rejects the continuation. Incident/receipt membership is stable across accepted continuations. Unattributed-pending/recent-run samples and live phase/byte/index values are explicitly current to each page, not members of a retained multi-page snapshot; they cannot authorize recovery. Legacy continuations bind the store, a hash of the fixed registry/quarantine markers, a creation cutoff and ordered position; disclose that legacy schemas lack an audit epoch and sample mutable run evidence per page. Known marker/generation changes invalidate those continuations. Complete authoritative review uses offline planning after upgrade, never a legacy diagnostic cursor.

Audit inspection enumerates retained records; it does not hide them merely because an audit deadline has passed. Dependency pins and bounded GC can retain them longer. Actual membership removal occurs through epoch-changing GC, and pruning receipts expose their retained summary plus incomplete-detail state.

`inspect --plan TOKEN` is an indexed **receipt lookup by plan hash**, not reconstruction or revalidation of an unapplied plan. Validate token syntax/store UUID, then return a retained applied/pruning receipt or `receipt_unavailable`. Absence is not proof that a token was never applied, because audit may have been legitimately pruned. Read-only lookup does not require the old filesystem binding to remain current, so historical receipts remain inspectable after a store move. To page through a plan before application, use `recover --cursor` under exclusive access and its configurable timeout.

Schema-8/9 adapters provide bounded diagnostic facts already supported by those schemas and `upgrade_required` guidance. They do not pretend to contain new attribution or dispositions. They never migrate and cannot issue a schema-10 application token.

Store paths shown as text are sanitized and bounded. Machine-readable owner selection is a validated argument value, not shell code. Human command examples must quote physical paths correctly; an unsafe/unrepresentable path gets explicit selection instructions rather than an executable-looking truncated command.

## Recovery plan

`capy runs recover [--cursor CURSOR] [--limit N] [--timeout DURATION] [--json]` without `--apply` performs nonmutating planning. `--project-dir` follows the existing explicit owner resolver. There are no partial run/owner selectors in v1.

Planning requires schema 10, the selected credential and exclusive administrative access. Acquire the permanent lifecycle lock exclusively without converting an existing shared flock; then acquire the permanent recovery lock and nonblocking owner-slot locks in the established order. Validate their identities and retain them through the read-only snapshot. A held/missing/unsafe lease refuses readiness. These locks are not process-quiescence proof and do not claim new owner generations.

Inventory every unresolved incident, relevant registry marker, abandoned nonterminal proof and work claim. Validate run identities and manifest copies. Include original outcome/proof, last durable phase, captured-prefix counters and TTL inputs needed by recovery; exclude command/output bodies. Classify subjects before producing a plan:

| Validated subject | Administrative action |
| --- | --- |
| Undisposed run with pending cleanup | Include a run disposition and resolve its reviewed incident(s). |
| Execution-terminal run with an open incident | Resolve the incident only; preserve the run's accepted proof and original expiry. Do not create a run disposition, freeze its index blob or renew output retention. |
| Nonterminal run with accepted scoped evidence | Leave it for ordinary bounded reconciliation, including its existing outcome/projection finalization; an associated open incident can be resolved separately. Do not fabricate a disposition for proven-safe work. |
| Valid owner/store marker without attributable run | Resolve an explicitly reviewed owner/store concern; no invented run identity or outcome. |
| Invalid identity/proof, missing required nonterminal child, mismatched claim or other unsupported inconsistency | Refuse the whole plan; acknowledgement is not repair authority. |

A fresh plan with no unresolved administrative subjects returns `no_recovery_needed`, no applicable token and no audit allocation. Proven-safe reconciliation backlog is reported separately. Replaying an already-applied token still follows receipt idempotency rather than creating an empty recovery.

Compute a canonical fingerprint over store UUID, schema version, policy revision, recovery revision, global/owner quarantine markers and the complete ordered recovery subject/evidence inventory, including each affected run's original generation, cleanup/result and prefix counters. Also bind a digest of the physical selected-owner path and acquired database/permanent-lock file identities (device/inode on the supported platforms). Revalidate opened descriptors against their paths while holding the locks. Moving/copying the store or replacing its database/locks invalidates application of an old plan even if the copied store UUID is unchanged; inspect and plan again. This is target binding, not process-origin or quiescence proof.

Use one canonical inventory builder for plan creation, page validation and apply. Sort by explicit subject kind and stable identity/generation; define fixed field order/types and null handling. Inferred subjects without a persisted incident use deterministic subject keys, not freshly generated UUIDs. Allocate their incident UUIDs and detection timestamps only inside apply. Exclude observation time, estimated future expiry, free-disk samples, pagination size/position, timeout, formatting and other presentation values from the fingerprint. Unchanged logical evidence must produce the same token across repeated previews and pages. Physical/quota capacity is rechecked at apply rather than trusted from a preview sample. Stream rows in batches of at most 64; do not retain every program or payload in memory. Incomplete inventory returns `recovery_inventory_incomplete` without an applicable token.

Offline planning defaults to a five-minute total context, matching the existing migration budget. `--timeout` accepts a positive finite Go duration such as `15m`; reject zero, negative, malformed or overflowing values before storage work. An earlier caller deadline still wins. Thread this context through the entire inventory and fingerprint operation rather than retaining a nested five-second or ordinary three-second recovery limit. The timeout changes only how long the same complete snapshot may be computed, not its validation, locks or fingerprint. On deadline, report the effective budget and an exact longer-timeout planning command for the same owner; reinspection alone is not the escape path. Interactive `inspect` keeps its separate two-second budget.

The token is an opaque, versioned, bounded representation of those identity/revision/hash fields (at most 1,024 bytes), not a permission credential or a claim that a human read the output. The complete fingerprint is computed even when response pagination omits subjects. Plan continuations contain that fingerprint and an ordered position; every page reacquires administrative access, rebuilds/compares the complete fingerprint, and only then returns the requested bounded page. Show total counts, omitted/continuation status and the exact `recover --cursor` command so the operator can review all subjects. Pages and apply reject a changed snapshot. No token or hidden snapshot is persisted by planning.

The plan identifies dispositions to be recorded, all remaining unsupported blockers, retention durations and estimated output/audit deadlines, that quota can evict output sooner, and whether the capacity sample is sufficient. Label preview deadlines as estimates based on preview time; immutable actual deadlines use the eventual successful `applied_at`. A non-applicable plan never includes a runnable apply instruction that bypasses its refusal. No preview success means that old execution groups have been verified stopped.

## Apply protocol

Syntax: `capy runs recover --apply --plan TOKEN --confirm-stopped --cleanup-basis groups_stopped|host_restarted --reason TEXT [--timeout DURATION] [--json]`.

All four confirmation/basis inputs are mandatory for apply; reject missing, unknown or conflicting arguments before storage changes. The basis describes an operator-established fact. `host_restarted` does not claim that Capy matched historical boot identity. The operator must establish that the relevant originating execution was stopped, including when a store was moved from another machine. When that is unknown, do not apply.

Application also defaults to a five-minute total context and accepts the same positive `--timeout` override, including for full inventory revalidation and commit. It must not retain a shorter 30-second or capture-write deadline inside the administrative path; a successful long plan must have a corresponding supported long apply path. The same exclusive lock order and earlier-caller-deadline rule apply. It authenticates and rechecks schema/store identity under those locks, without the MCP service or ordinary maintenance attachment.

Within one transaction acquired through `sqliteutil.BeginImmediateContext(ctx, db, "runs")` using the administrative context:

1. Validate token target binding before mutation. Look up an existing receipt by exact plan hash. If present, verify its store binding and compare the normalized method/basis/explanation with the recorded action. A differing attestation returns `recovery_receipt_conflict` with the existing receipt ID, never an audit rewrite. Otherwise return its immutable summary without renewing timestamps or charges, including when the receipt is marked pruning. Report that pruned details may be unavailable rather than treating missing members as permission to reapply. Also report current unresolved blockers; old success does not imply no later incident exists.
2. Otherwise recompute and compare the full plan. Any material change, unsupported inconsistency or incomplete inventory aborts without dispositions or cleared flags.
3. Reserve/transfer bounded audit charges and check physical/quota capacity without retention. Capacity failure names the offline quota-increase/space procedure; it never discards evidence.
4. Materialize missing inferred/legacy incident subjects and insert one receipt plus immutable membership/disposition evidence for the reviewed uncertain runs, initializing their separate payload-retention state to `retained`. Save the byte-exact result snapshot/digest and seed the separate disposed-run index state. Preserve original result blobs, cleanup pairs, execution terminal/completion/expiry, programs, raw events and existing projection coordinates.
5. Mark the reviewed incidents administratively resolved. Derive affected batch operational metadata. Clear relevant registry markers only when that generation has no unresolved incident or unsafe undisposed work. Recompute the global admission marker from all unresolved operational blockers and increment recovery revision in this same transaction. A plan containing unsupported blockers cannot partially succeed.
6. Commit. Close database handles before releasing permanent locks, without reconciliation, retention, checkpoint-driven reclamation or command execution.

Execution writes and batch dispatch must reject an administratively closed historical run. Index writes must reject stale historical owner generations and cannot mutate execution facts; fresh healthy owners may perform the narrowly scoped index work defined below. Normal slot reuse can publish a fresh generation only after its old operational blockers are gone. Existing service latches are not cleared in place; operators restart affected services.

Matching abandoned index claims can be released by ordinary generation-validated reconciliation after restart; a disposition must not make a mismatched claim safe or authorize its deletion.

If commit outcome is uncertain, return `recovery_outcome_unknown` with a read-only receipt lookup by plan token. Repeating the same apply is safe while its receipt is retained. Once audit history has legitimately been pruned, an old token is stale; it cannot create another disposition or retention window.

## Operational consumers and public results

Keep public envelope version 2, cursor/redaction versions and private helper protocol 2. Add optional structured `recovery` metadata to affected run/batch summaries, read subjects and search coverage, and a bounded `recovery_hint` to relevant errors. The fields distinguish unresolved from operator-resolved, expose receipt ID/time/basis, administrative retention/closure and whether the incident blocks admission. They are essential when present, not optional preview text.

Original `state`, exit/signal, `CompletedAt`, `Capture.TerminalPersisted`, cleanup and execution-terminal validation retain their historical meaning. Read projections of uncertain runs continue to identify capture as incomplete and cleanup as uncertain, with explicit operator-resolution context; the stored original result is not rewritten. Human output uses “last recorded” language.

Hooks continue to observe execute/fetch responses only; status/read/inspect cannot create routing evidence. As a defensive boundary, `healthyRunEnvelope` rejects the presence of `recovery` regardless of whether its value is an object, null or malformed. `healthyExecuteObservation` treats that field as a structured-envelope marker, so it cannot rescue a recovery-only object through legacy fallback. Healthy execution envelopes without recovery context omit the field entirely rather than emitting `recovery:null`. Do not inspect arbitrary printed output for this field or change fetch/healthy legacy behavior. Task 9 tests root/child observations, v1/v2 and both cleanup scopes, malformed recovery values, query-tool exclusion and healthy controls.

Reconciliation excludes exact disposed historical rows from unfinished operational work and generation-mismatch quarantine; it does not ignore genuinely inconsistent unrelated rows. Owner reuse resets only the derived marker for the reusable slot, while the incident/disposition preserves original generation attribution.

For batches, keep original per-child result/proof/terminal copies. A missing nonterminal child is allowed only when a retained disposition snapshot proves its exact identity and carries a durable `payload_state=evicted` transition committed with parent-row deletion; a receipt alone or missing `retained`/`evicting` row is insufficient. Otherwise keep the existing error. Compute administrative closure separately when all children are terminal or disposed. Historical cleanup aggregation remains pending when any original child proof is pending. Report recovered-child counts separately, and exclude disposed children from any current-concurrency presentation. Never set original `CompletedAt` or describe administrative closure as successful execution.

Recompute batch operational closure both during apply and in the same transaction as every later ordinary child-terminal transition, including `recoverRun`/`syncBatchChild` reconciliation. A disposed child plus a proven-not-spawned sibling left for reconciliation is not yet operationally closed at apply; when that last sibling is safely finalized after restart, record the first administrative closure time and batch expiry exactly once. Repeated reconciliation cannot renew them. A batch with no disposed children keeps the existing execution-terminal completion path. This prevents resolved mixed batches and their referenced audit records from remaining protected indefinitely.

`status/list/read/search` consistently use administrative availability/retention for disposed payload. Ordinary execution APIs do not accept a recovery receipt as execution proof. After payload deletion, ordinary run reads report unavailable with an incident-inspection pointer while the audit record remains. Batch summaries retain their existing `output_available=false` behavior plus disposition context.

### Capture and projection boundaries

Apply does not append output, flush an unfinished sanitizer checkpoint or regenerate projection. Preserve only the existing safe projection; withheld tails remain withheld. Raw access still requires explicit unsanitized base64. Search indexes only existing sanitized coverage and reports partial coverage where projection is unfinished.

Keep the existing execution-based `eof` meaning. A separate `recovery.capture_closed=true` tells updated readers that no further capture is expected even when original completion is unknown; `end_of_available` can then stop polling without fabricating EOF/terminal proof. Existing cursor coordinates remain valid for available bytes. New status/help text explains this distinction.

After disposition, `runs.result` is byte-immutable until payload eviction. Validate a retained row against the stored result snapshot/digest plus its bound store/run/generation, cleanup columns and original terminal bit before overlaying any current index or recovery view. No exception permits an index worker to rewrite that blob.

A fresh healthy indexing owner may claim disposed retained output once store admission is healthy. Validate the worker's acquired lease/current registry generation and matching `run_work_claims` tuple; it need not match the historical execution generation. Existing per-stream progress/windows/FTS remain mutable. Aggregate state, coverage cursor and safe error metadata are written only to `run_search_state`. `ClaimIndex`, `saveIndexResult`/`failIndex`, index batches and abandoned-claim reconciliation must all branch to that destination for disposed runs. Reconciliation retains its free-slot/matching-generation rule for abandoning a worker claim. Neither branch introduces a new weaker execution-update path.

Status/list/read/search overlay the separate index state into returned views and use the shared effective-retention predicate. Non-disposed runs keep their current indexing contract. A missing disposed-run index-state row is an explicit metadata inconsistency, not permission to rewrite or silently fall back to the frozen blob. Remove that index state with payload under the bounded accounting rules; independently retained audit snapshots remain unchanged. Tests compare stored result bytes/digest across first search, resumed search, quota/error paths, worker-loss recovery and slot reuse.

## Retention and accounting

- Unrelated completed-run deadlines and eligibility do not change. Recovery does not renew them. Output already legitimately evicted cannot be restored.
- An attributed unresolved run incident protects its still-retained run row/payload from ordinary expiry/quota deletion, even if terminal evidence arrives after incident publication. Reads expose that protected retained evidence with incident context without changing its original expiry. Resolve such an incident without a run disposition when the run has accepted terminal proof; afterward its original expiry/eligibility resumes, even if already expired. This protects the evidence needed for a complete plan without renewing unrelated history. A run-scoped incident missing its required run evidence remains inconsistent; owner/store-scoped legacy incidents do not invent that evidence.
- For each disposed uncertain run, fix `retention_expires_at = applied_at + its admission-recorded TTL`. This administrative field does not replace original `ExpiresAt` or `CompletedAt`. Effective payload expiry uses it once disposition exists.
- Disposed payload becomes quota-evictable under the existing oldest-eligible policy; use administrative resolution time for its ordering. Recovery's own transaction never calls retention. Later ordinary maintenance/admission can evict expired or pressure-selected history, as the plan states.
- A compact receipt/incident/disposition remains protected until its administrative deadline and while any retained run, child manifest or other incident-resolution reference requires it. Each run-related member uses that run's admission TTL for its audit deadline, including incident-only resolutions with no new payload-retention deadline; owner/store-only members use the stored policy TTL at application. A receipt deadline is at least the maximum of its member deadlines. Deadline/identity dependencies cannot be renewed by reads, retries or later policy edits.
- Once all children are operationally closed, a batch with disposed children gets separate administrative closure/expiry using its admission-recorded batch TTL. Existing terminal batches keep their original expiry. Its manifest can be evicted under quota/expiry only when every child is operationally closed and every needed disposition is independently retained.
- Delete payload/index rows in the existing bounded tombstone batches. Atomically set the run tombstone and disposition payload state to `evicting`; keep the full payload debit until removal completes. In the final deletion transaction, transfer retained audit debit to independent accounting, mark payload `evicted` with its time/cause, and delete the parent run. These changes must commit together. Do not lose audit/eviction evidence through a cascading foreign key or charge it twice. A present row paired with `evicted`, or an absent row paired with `retained`/`evicting`, is inconsistent rather than assumed legitimate eviction.
- Charge bounded records explicitly, including recovery receipts and memberships. Existing run reservations may fund transferred bounded metadata, but the implementation must verify that bound rather than assume all cases are free. Recompute the current dbstat/conservative debit after changes. Independent audit metadata and schema/index overhead must not become an unbounded uncharged store.
- Prune an entire receipt group only after its maximum deadline and after retained run/batch references to its members are absent. Mark a group as pruning before bounded deletion, retain its plan-hash tombstone/receipt identity until all dependent rows are removed, and remove the root receipt last. A partially pruned group cannot be reapplied or mistaken for a new unresolved incident. Retained audit may exhaust quota; report that accurately. Do not destroy protected evidence or misreport usage to admit work.
- The offline `upgrade` quota-increase mode permits explicit configured growth without eviction even while quarantined. It refuses TTL/per-run-limit changes and quota decreases; it reports revision changes and invalidates old plans. Disk-full or metadata-capacity failure keeps history and quarantine intact.

## Upgrade and compatibility

Schema 10 adds the records/indices and rebuilds the runs table to establish the required no-default `last_phase` column. Copy legacy phase as explicit `unknown`, preserving original payload/result bytes, row IDs, store UUID, indexes and foreign-key relationships. Include the table-copy/WAL cost in headroom checks. A new current-schema fixture and the actual frozen schema-8/9 fixtures must validate the transition, including pending history, retained batch copies and rejection of fresh inserts that omit phase.

`capy runs upgrade [--json]` resolves the existing selected credential, acquires exclusive administrative ownership and performs no execution admission. It never initializes a missing store. Supported paths are 9→10 and 8→9→10 using the existing validated 8→9 transformation followed by the new migration. Each committed step preserves quarantine/history; interruption between steps leaves a valid supported intermediate schema and an actionable retry. Do not claim that both separate migration commits roll back together.

Freeze the 8→9 destination DDL/column list and target-version checks at schema 9. The current `migrateSchema8` derives its destination from the shared fresh-store `runTableSchema`; after that constant becomes schema 10, its old INSERT would omit required phase metadata. It must instead use a version-pinned schema-9 definition, then run the separate 9→10 migration. Concurrent-upgrader handling must recognize the completed stage by its explicit target version and unchanged store identity, not assume every intermediate stage targets the current global schema constant.

For the explicit offline command, validate any configured quota increase and commit it against the **currently authenticated schema 8, 9 or 10 before migration capacity checks or copying**. Use a dedicated policy transaction under exclusive administrative access, with no reconciliation/retention and no new-schema table dependency. Reload the increased policy before each migration stage. The increase changes only retained quota and policy revision and may remain committed if a later migration fails; report that side effect and the valid remaining schema explicitly. No history or quarantine is removed. This avoids requiring a successful migration before the quota increase needed to make that migration possible. Automatic execution migration uses the stored quota and directs capacity failures to this explicit offline procedure; it does not silently apply that administrative increase.

Use bounded contexts, identity rechecks, private temporary behavior and preflight headroom. Publish schema/policy markers last in each transaction. A failure cannot trigger deletion to make migration fit. Capacity preflight and optional explicit quota growth must work without normal policy-change reconciliation/retention. Inspection/planning on old schemas only reports the offline command; helpers and ordinary readers never migrate.

Normal authenticated configured execution attachment (`OpenWithPolicy` with creation/admission enabled) automatically attempts the same supported 8→9→10 or 9→10 migrations before admission. Exclusive ownership, identity, capacity and caller-deadline conditions are mandatory; failure refuses execution rather than falling back. Readers/helpers/inspection never migrate. An execute against quarantined history can therefore upgrade the schema and still be refused without a run ID or spawned command; migration preserves the quarantine and does not imply recovery. Ordinary attachment's subsequent maintenance remains distinct from the migration transaction and from the maintenance-free offline operator path.

The operator workflow uses `upgrade` as the no-submission alternative and rechecks the actual schema before deciding whether it is needed. Task 15 must replace the old AGENTS.md execution-only migration invariant with both authorized entry points; do not change that runtime invariant text before implementation exists. Older binaries refuse schema 10. Downgrade requires a compatible reader for retained data; existing explicit discard remains the destructive option after cleanup. No reverse migration or credential rotation is introduced.

## Refusals and operator guidance

| Condition | Required action and meaning |
| --- | --- |
| `cleanup_unverified` before admission | State that no command was admitted; identify known blockers/counts and direct to `capy runs inspect` for that owner. Retained completed logs remain recoverable subject to ordinary retention. |
| `storage_busy` / recovery lease held | Stop the identified store users/helpers and retry inspection/planning after shutdown. Do not equate a stored running row with a live PID. |
| Credential unavailable/wrong key | Restore the selected matching credential and reload affected processes. Do not automatically reset, migrate, fall back to a different key or call this a cleanup fix. |
| `upgrade_required` / unsupported schema | Use the compatible binary and explicit offline upgrade; never submit a command to force repair. |
| `recovery_plan_stale` | Reinspect and review the changed set; do not apply the old confirmation to new incidents. |
| `no_recovery_needed` | No applicable token, receipt or mutation. Report any proven-safe reconciliation backlog separately; do not manufacture an operator action just to produce a receipt. |
| `receipt_unavailable` | No retained receipt matches that receipt UUID or plan hash. This is not proof of nonapplication; inspect current incidents and, for an unapplied plan, obtain/review it through `recover` rather than treating receipt lookup as plan validation. |
| `recovery_receipt_conflict` | The plan already has a receipt with a different normalized cleanup basis/explanation. Show its receipt ID and inspection command; do not overwrite history or claim the new attestation was recorded. |
| `recovery_inventory_incomplete` | No applicable token. For a scan deadline, show the effective timeout and the exact same-owner `capy runs recover --timeout 15m` form (increase further when needed), keeping all store users stopped. An earlier caller deadline must also be raised by that caller. Metadata/read failures name their actual repair; do not suggest that more time repairs inconsistent data. |
| `recovery_timeout` before commit | Transaction rolls back without dispositions or cleared flags; show the same apply command/token with a larger `--timeout`. Revalidate the complete plan on retry. If commit outcome is uncertain, use `recovery_outcome_unknown` instead. |
| `recovery_inconsistent` | Preserve diagnostics and resolve the named identity/proof/manifest inconsistency separately. Operator confirmation cannot override it. |
| `recovery_capacity` | Show required/available accounting or filesystem headroom and the explicit configuration-increase/offline-upgrade procedure. No recovery-driven eviction. |
| Cleanup cannot be established | Remain blocked. Explain that the operator must investigate/stop originating execution; a guess, free lease or missing PID is insufficient. |
| `recovery_outcome_unknown` | Inspect receipt by plan token; do not assume success or repeat execution. Reapplying the same retained token is idempotent. |
| Applied/already applied | Show receipt and current admission status, original uncertainty, retention deadlines and restart/verification instructions. Later incidents can still block admission. |

An applied receipt reports the cleanup gate's current state, not a guarantee of future quota, credential, sandbox or command success. Proven-safe nonterminal siblings may still require ordinary bounded reconciliation after restart; report that work separately from unresolved cleanup rather than fabricating their completion during apply.

Preserve actionable code and next step in the minimum 2-KiB serialized response budget. Error data must not contain programs, captured output, raw stored/backend errors or secrets. MCP has no recovery-apply capability; it instructs the operator to use an ordinary terminal.

## Query and response boundaries

Share metadata-query and formatting logic, not the top-level inspection opener, with admission. An admission error raised inside a SQLite transaction must collect any bounded hint through that transaction's query interface or already-available incident context. Do not open a second inspector/lease or request the store's one-connection pool while its transaction holds the connection. If bounded detail is unavailable, preserve the authoritative refusal and next inspection action with an explicit detail-unavailable marker. Outside a transaction, use the existing authenticated connection/context without recursive attachment or reconciliation.

Execute upgrade, plan computation and apply once per command before response-budget rendering. Budget builders only shorten the captured in-memory result; they never rerun an administrative operation, recompute a plan or perform another database mutation. If response delivery fails after commit, use the receipt/plan lookup and idempotent retry contract. Response shortening is not an execution retry and cannot change the committed outcome or counters.
