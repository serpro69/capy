## P1 findings

### 1. Changed files and fetched Markdown can bypass the proposed chunker

**INCONSISTENT · Confidence 10/10.** The design includes refreshed files and fetched writes. The plan changes store parsing. A changed file refresh calls the chunker with the type stored on its old source. The fetcher forces plaintext for `text/markdown`. I observed a file changed from plain text to a two-heading manual refresh as `plaintext / Output`. Fresh indexing of the same bytes gave `markdown / Guide > Quartz`. Sending the manual through the fetch dispatch as `text/markdown` also gave `plaintext / Output`. The HTML and JSON fetch controls reached their expected parsers. [Compatibility promise](design.md#compatibility-and-acceptance) · [File writes](../../../../internal/knowledge/index.go#L52) · [Refresh](../../../../internal/store/stale.go#L116) · [Fetch dispatch](../../../../internal/server/tool_fetch.go#L368)

Specify format selection at each entry point. For ordinary auto-detected files whose sanitized hash changes, select the type for the changed content and persist it with the replacement. Preserve the file identity check around that write. Route an explicitly Markdown response to Markdown and keep an ordinary `text/plain` response on its existing path. Clarify that whole-document parse failure takes the plaintext fallback once JSON was selected. Inline auto-detection currently recognizes only valid objects and arrays. Specify the result for same-hash revalidation and make the two differing write paths acceptance cases. [Conditional replacement](../../../../internal/store/index.go#L155)

### 2. Per-section part numbers still let rank fusion collapse different sections

**TECH_RISK · Confidence 10/10.** The design gives continuation parts distinct suffixes. Two sibling sections headed `Fixture` have the same path and can each have a first part. JSON batches can also repeat an ID, and different long paths can share a 256-byte prefix. The collision matters even when both mirrors stored the correct bodies. My two-section fixture stored two `Guide > Fixture` rows. A source-scoped query matching both returned one hit with the requested result limit and per-source allowance both set to ten. Fusion uses the full stored title as part of its key and keeps one body. [Title requirement](design.md#markdown) · [JSON batch titles](../../../../internal/store/chunk.go#L411) · [Fusion](../../../../internal/retrieval/retrieval.go#L327)

Define uniqueness over the final titles of distinct new chunks **within one source**, including unsplit sections and JSON batches. A deterministic source-wide ordinal on collisions can preserve the ordinary short titles. Reserve space for the suffix and resolve collisions with literal user headings too. Check that one shared-term query returns both distinctive answers. Changing the shared retrieval identity would also touch the vault and is a much larger decision.

### 3. A 256-byte stored title can remove the only searchable copy of a term

**MISSING · Confidence 10/10.** A Markdown heading with a body is ordinarily removed from the body. After JSON object decomposition, a long field name can likewise appear only in the title while its value occupies the body. In the current store a query for the last word of a 315-byte heading path returned the expected section. Its ten-byte body contained none of that word. Persisting only the proposed display prefix would lose this existing hit. An ordinal fixes the collision in finding 2 but cannot match the missing word. [Title budget](design.md#json) · [Markdown heading handling](../../../../internal/store/chunk.go#L77) · [JSON field handling](../../../../internal/store/chunk.go#L334) · [Indexed columns](../../../../internal/retrieval/retrieval.go#L170)

Distinguish the display budget from searchable content. Specify where the original heading or field name remains searchable, including a name that exceeds one body. For example, bounded bodies can retain the heading text or field key once while titles carry a short path and coordinates. Require a suffix-only query to return the intended section and verify that its result still identifies the leaf or record.

### 4. Splitting an oversized record by field can multiply the number of FTS rows

**TECH_RISK · Confidence 9/10.** The plan prevents repeated serialization of a growing array batch. It leaves the object recursion policy open. A 4,497-byte single-record array currently makes one oversized chunk. Feeding the same 161-field object to capy’s existing object walker produced **161 chunks**. Reusing that walker for oversized rows would create 161 inserts in each mirror for a record that can fit in a few groups. The walker also pretty-serializes each object before deciding to recurse, including non-flat parents whose serialized form it discards. The 161-row count measures the existing object walker. The proposed array implementation could avoid that cost. [JSON plan](implementation.md#json-ingestion) · [Object walker](../../../../internal/store/chunk.go#L324) · [Mirror inserts](../../../../internal/store/index.go#L221) · [Source-size rationale](../../../adr/022-source-size-guard-and-db-bloat-prevention.md)

Pack neighboring fitting fields into deterministic bounded groups with their record identity. Descend when an individual field or element needs splitting. Bound intermediate serialization and path construction as well as the emitted body. Add the wide, ordinary record alongside the planned array-of-small-rows case. Check row count and recovery of a field near each end. This addresses the growth without a new operator quota.

## P2 findings

### 5. The JSON fragment representation and filter behavior need a worked example

**INCOMPLETE · Confidence 9/10.** UTF-8-safe cuts alone can divide a JSON escape sequence. It matters whether the indexed text represents the encoded token or the decoded value, where the record identity appears, and how a caller recognizes a continuation. Current array chunks are classified as code, while an oversized primitive from the object walker defaults to prose. A number-preserving decoder also changes the value type used by `findIdentityField`, whose accepted types currently exclude `json.Number`. In the baseline, the integer `9007199254740993` already produced the incorrect title `(root) > 9.007199254740992e+15`. [Fragment requirement](design.md#json) · [Primitive handling](../../../../internal/store/chunk.go#L297) · [Identity selection](../../../../internal/store/chunk.go#L391) · [CLI type filter](../../../reference/tools.md#knowledge-search-from-the-terminal)

Show the stored title, body and code/prose classification for a complete batch, a decomposed row and consecutive pieces of an escaped scalar. Specify the outcome for a row that fits alone but exceeds the cap inside array brackets, and for oversized elements in mixed or nested arrays. Apply existing redaction to complete searchable values before splitting any newly decoded representation. Check exact numeric IDs in both bodies and titles, and retrieve a distinctive value together with enough identity to tell which row it belongs to.

### 6. Automatic detection can normalize away the evidence the fence recognizer needs

**AMBIGUOUS · Confidence 9/10.** The current detector trims the entire document, then trims each candidate line. The first step alone loses the indentation of a fence on the first line. The heuristic uses `SplitN(..., 50)`, whose final element is the unsplit remainder. The proposal requires an opener with up to three spaces and allows a single genuine opener to trigger Markdown, but leaves the scan horizon and backtick info-string rule implicit. A line beginning with an inline backtick span could turn all following prose into code. [Markdown contract](design.md#markdown) · [Current detector](../../../../internal/store/detect.go#L9) · [CommonMark fence grammar](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)

Have detection and chunking inspect the same original lines and say how far automatic fence detection looks. Check a four-space-indented first line, a same-line backtick span, a fence after a long introduction and a shebang control. Set classification from the blocks present in each emitted chunk, so an interior code continuation is available through `--type code` and a prose-only continuation of the same section through `--type prose`. State whether oversized example fragments repeat delimiters and account for any repeated bytes.

### 7. The benchmark cannot measure two of the acceptance claims

**INCOMPLETE · Confidence 10/10.** Task 3 asks for a quality comparison and the implementation plan calls out indexed chunk counts. The 12 Markdown quality fixtures are 674–891 input bytes and the 10 JSON fixtures are 444–753 bytes. The report has no per-source chunk count. Its recall scorer searches the full stored body. A green result can therefore coexist with excessive partitions or an answer missing from the CLI’s 1,500-byte prefix. The proposed tests in Tasks 1 and 2 are appropriate places to cover this. [Verification plan](implementation.md#verification) · [Feature tasks](tasks.md#task-3-verify-and-document-the-feature) · [Benchmark metrics](../../../../internal/store/bench_test.go#L37) · [Relevance scorer](../../../../internal/store/bench_test.go#L322) · [CLI renderer](../../../../cmd/capy/search.go#L139)

Keep the immediate-baseline quality comparison for existing inputs. Add direct checks for partition counts, body byte lengths and ordered title/body/type equality across the two FTS mirrors. Grade a real search reply on the distinctive example or field **and its identity**. For a long scalar, check ordered coverage in storage and query representative parts with distinct terms. This gives an acceptance condition the feature can meet with today’s search limits and excerpt renderer.

## Feasibility and checks that passed

The normal store writer sanitizes, chunks and then submits the same slice to both FTS tables in a single transaction. Same-hash writes retain historical rows, and file refresh already has a guarded commit. The vault has a single production dependency on `store.SplitOversized` for oversized turn windows. A knowledge-only block packer, coupled with exact-label eviction and reindex when an operator retains the original, fits these boundaries. The Markdown and JSON tasks each deliver an index-to-search path. Their task sizes, dependencies and final verification step are coherent. [Store writer](../../../../internal/store/index.go#L50) · [Vault caller](../../../../internal/vault/chunker.go#L108) · [Operator procedure](../../../reference/tools.md#cleanup-and-older-chunks) · [Task graph](tasks.md#dependency-graph)

I ran focused Go/FTS5 probes with synthetic credentials and temporary fixtures against the current store, search and fetch dispatch. The reported sizes and query outcomes are baseline observations. Post-change benchmark deltas and end-to-end acceptance remain implementation checks. The original recommendation was to resolve the four P1 decisions and add acceptance cases for the three P2 findings before implementation.

## Resolution after recheck

All seven findings were confirmed against capy `6677d7b`. A fresh run of the temporary FTS5 probes reproduced the differing refresh/fetch selections, the two-row/one-hit collision, the term present only in a 315-byte title, the numeric ID rounding and the 161-field fan-out. Inspection of the detector, filter, benchmark corpus and scorer confirmed the remaining contract and verification gaps. The observations above describe the original proposal.

| Findings | Decision in the revised documents |
| --- | --- |
| 1 · Write paths | A changed file is re-detected from its new raw bytes and committed under the existing guard. Native and converted Markdown have explicit fetch routes. Same-hash writes retain the previous representation. [Format selection](design.md#selecting-a-format) |
| 2–3 · Titles and searchable text | Final bounded titles are unique per source, including generated/literal collisions. Heading bodies and retained JSON keys preserve search terms beyond the title budget. [Stored sections and titles](design.md#stored-sections-and-titles) |
| 4–5 · JSON packing and representation | Compact arrays and field groups use actual byte costs. Worked examples define exact numeric identity, an escaped scalar, fragment order and filter behavior. [JSON contract](design.md#json) |

The design, implementation plan and task dependencies are ready for implementation. The runtime checks in the revised plan are acceptance criteria for that work.
